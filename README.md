# Plex302 · Plex 云盘 302 直链助手

[![build](https://github.com/celestial520/plex302/actions/workflows/docker.yml/badge.svg)](https://github.com/celestial520/plex302/actions/workflows/docker.yml)
[![image](https://img.shields.io/badge/ghcr.io-plex302-blue)](https://github.com/celestial520/plex302/pkgs/container/plex302)
[![license](https://img.shields.io/badge/license-MIT-green)](LICENSE)

Plex 通过 **CloudDrive2 挂载**直接扫描 115 网盘里的真实文件（**不生成 strm、不下载、不整理**）；播放时把 `/library/parts` 请求 **302** 到 115 直链，NAS 不中转视频流量。

播放凭据走 **115 开放平台官方接口**（扫码登录，和 plex-demo 同一条链路）；入库走 **115 操作事件**（网页 Cookie）——两者分离，各管一段，谁也拖不累谁。

> 一句话：**播放全走官方 API，入库靠事件流水。** 官方接口看不到「移动」，所以 plex-demo 会漏的整理，这里不会。

## v1.8.0 重写要点

这是一次按 plex-demo 架构重做的版本，只保留它验证过的部分，把它的短板换掉。

| 能力 | plex-demo | Plex302 v1.8.0 |
|---|---|---|
| 文件入库方式 | CD2 挂载真实文件 | ✅ 同 |
| 302 拦截 | nginx + njs 拦 `/library/parts` | ✅ 同（v1.7.0 已对齐） |
| 直链来源 | 115 开放平台 `folder/get_info` → `ufile/downurl` | ✅ 同，**扫码登录，client_id 复用，不用自己申请** |
| 直链缓存 | nginx 共享内存 + 内存缓存 | ✅ 同，另加 Python 侧单飞 |
| 失败回源 | 418 → 回源 Plex | ✅ 同 |
| strm / 整理 / 重命名 | 有 | ❌ **不要** |
| 局部入库 | 定时扫「最近上传」，10 分钟一轮 | ❌ **换掉**：改成事件流水，见下 |
| 移动 / 改名识别 | ❌ 识别不出（官方接口只看上传时间） | ✅ 事件里有 `move_file` / `file_rename` |

### 为什么「定时扫最近上传」一定会漏

plex-demo 的判断依据是文件列表里的 `uppt`（上传时间），它每隔 N 分钟问一次「最近 N 分钟有没有新上传」。而 CMS 的整理流程是：

```
上传到 /待整理  →  （plex-demo 扫到了，但这里不是 media，不入库）
                →  CMS 识别、改名、移动到 /media/电影/xxx
                →  下一次扫描：这个文件「上传时间」没变，不在「最近上传」窗口里
                →  漏
```

只要「上传」和「移动到 media」跨过那一次扫描的时间点，就一定漏。把间隔调到 1 分钟也只是降低概率，因为移动永远不算上传。

### 这里的做法：盯事件，不盯上传时间

```
115 操作事件流水（Cookie，/behavior/detail）
  ├─ upload_file / receive_files → 新文件
  ├─ move_file / file_rename     → 路径变了，pickcode 没变
  ├─ copy_file / copy_folder     → 新副本
  └─ delete_file                 → 从索引移除
        ↓
  事件自带 pickcode + parent_id
        ↓
  用 parent_id 反查「现在的目录」→ 映射成 Plex 路径 → 只扫这个目录
        ↓
  目录静置 90 秒再扫（CMS 还在整理就继续往后推，最长 600 秒）
        ↓
  扫完再复核一次（默认 180 秒后）
```

六个保险叠在一起，「移动进 media 的那一下」不会漏，而且**出事也不会静默漏**：

1. **事件是流水不是窗口**：游标增量拉取，移动、改名一条不漏，不依赖上传时间。
2. **旧路径也刷**：移动/改名时用 pickcode 反查索引里的旧路径，旧目录同样排队扫一次，Plex 才会把旧位置的条目删掉。
3. **静置 + 复核**：目录里还在动就不扫，扫完 3 分钟再确认一次，接住「扫的时候文件还没写完」。
4. **游标绝不跳条**：单轮拉不完（超过 3000 条）时游标原地不动，下一轮把翻页预算翻倍继续追更旧的，追平才前进；只有积压超过 2 万条才显式放弃并告警。
5. **处理失败会重试**：反查目录 / Plex 报错时**不写「已处理」标记**，游标也不推进，下一轮重试，连续 5 轮才放弃并推送告警。旧版本这里会直接标记已处理 —— 一次网络抖动就是永久漏，且日志里看不出来。
6. **每日全量兜底（默认关闭）**：可在设置里打开，04:30 整库扫一遍。整库扫等于让 CD2 把 115 目录全读一次，是和 CMS 抢额度最狠的一步，所以默认关；事件流水正常时基本不需要它。

### 官方接口为什么做不到，Cookie 事件怎么补的

115 开放平台（OpenAPI）只有「按路径查文件」「取直链」这类**点查**接口，**没有「最近操作记录」接口**。所以 plex-demo 这种纯官方接口的方案，只能靠「按上传时间扫最近 N 分钟」去猜哪些文件变了 —— 而“移动”不改变上传时间，这是接口能力的天花板，作者说“没办法”是准确的。

本项目的分工是：

| 环节 | 用哪套凭据 | 原因 |
|---|---|---|
| 播放取直链 | **扫码登录（OpenAPI）** | 按完整路径 1 次定位，不列目录、不占网页风控额度 |
| 局部入库（增删改移） | **115 Cookie（网页版 `/behavior/detail`）** | 只有网页版有操作流水，这是官方接口拿不到的东西 |
| Cookie 失效兜底 | 回退到逐级列目录 | 保证 Cookie 还能用；官方接口挂了也不影响入库 |

两套凭据各管一段、互不替代：扫码只为了播放，Cookie 只为了入库。Cookie 那部分只会被事件轮询用到（60 秒一次，带抖动），不参与播放。

### 风控预算（和 CMS 共用同一份 Cookie）

| 动作 | 频率 | 每天上限 |
|---|---|---|
| 事件流水 `/behavior/detail` | **可调**，默认 60 秒（带抖动） | 默认 ~1440，设 1 小时则 ~24 |
| 最近文件 `/files/recent` | **默认关闭**，可选开启 | 0 |
| 播放取直链 | **不走这里**，走 `proapi.115.com` 开放接口 | 0 |

- 所有 Cookie 请求串行 + 每次间隔 2.05 秒起、加 0~20% 抖动，不做机械节奏。
- 容器启动后**先等 40~55 秒**再开始第一次拉取，避开 CD2 挂载和 Plex 扫库的高峰。
- **拉取间隔可以自定义**（设置 → 增量入库 → 检查间隔，1 分钟 ~ 6 小时）。间隔只影响「多久发现变化」，不影响完整性：游标是增量的，拉得慢只是晚一点入库，中间不会跳条。
- 收到 405 立刻全局停手：60 秒起，连续命中翻倍，最长 15 分钟，半小时无命中才复位。
- **可选接口被拦不会触发全局停手**：「最近文件」这类兜底接口 405 时只跳过本轮，不影响事件流水。

#### 关于 405：先分清是哪一种

115 的 405 有两种，含义完全不同，别一看到就以为账号要废了：

| 表现 | 含义 | 该怎么办 |
|---|---|---|
| HTTP 405 + **HTML 页面** | 反爬拦截页。115 对 `/files*` 这类高频接口有单独规则，**同一份 Cookie 打别的接口往往正常** | 只影响被拦的那条路径；等一会或不用这条接口即可 |
| HTTP 200 + JSON 里带 405 / “访问频繁” | 登录态或频率层面的限制 | 停手等 5~10 分钟，别继续猛打 |

判断方法：同一时刻 `/behavior/detail` 能返回数据、只有 `/files/recent` 报 405，那就是**接口级拦截**，不是账号级风控，CMS 也因此完全不受影响。本项目从 v1.8.4 起把这类情况独立处理，不会再写一条“请暂停 CMS”的误导日志。

> 如果你确实看到 `/behavior/detail` 也在报错、同时 CMS 也开始卡，那才是整号级别的风控，这时才需要停手。
- 概览页有「115 请求预算」一栏，能直接看当天发了多少次；超过 5000 次会标红。
- **整库全量扫描是最重的一步**，默认关闭；真要开建议先用「立即全量扫描」手动跑一次，观察当天请求数再决定要不要定时。

## 架构

```
                        ┌──────────────────────────────┐
  Plex 客户端 ──32400──▶│  Plex（扫 CD2 挂载的真实文件）│
                        └──────────────────────────────┘
                                    ▲ 扫描/刷新
                                    │
   Plex 客户端 ──32500──▶┌──────────┴───────────┐
   （自定义访问 URL）     │  nginx + njs（Plex302）│
                        │  /library/parts 拦截   │
                        └──────────┬───────────┘
                          命中缓存 │  未命中
                                   ▼
                        ┌──────────────────────┐
                        │  Python 后端 :999/内  │
                        │  路径 → pickcode      │──▶ 115 开放平台（扫码 token）
                        │  pickcode → 直链      │──▶ 115 网页 Cookie（事件入库）
                        └──────────────────────┘
```

- **播放**：njs 命中共享内存直链 → 直接 302，后端都不问；未命中才回后端解析一次。
- **入库**：事件监听发现目录变化 → 调 Plex 的「扫描这个目录」，不动整库。
- **兜底**：任何一步失败都回源 Plex，播放器看到的永远是「能播」。

## 快速开始

```yaml
services:
  plex302:
    image: ghcr.io/celestial520/plex302:latest
    container_name: plex302
    network_mode: host          # 必须 host：要拿客户端真实 IP，还要直连 CD2 gRPC
    restart: unless-stopped
    environment:
      TZ: Asia/Shanghai
      NGINX_PORT: 32500         # Plex 客户端以后连这个端口
      WEBUI_PORT: 999           # 管理页面
    volumes:
      - ./config:/config
      - ./log:/var/log/nginx
```

```bash
docker compose up -d
```

打开 `http://NAS的IP:999`，初始账号 `admin / admin`，登录后立刻改密码。

> 不需要给这个容器挂任何媒体目录：它不做文件读写，只做路径字符串映射和反代。

**端口冲突**：`network_mode: host` 会和旧的 plex-demo 抢 32500 / 999，先 `docker stop plex-demo` 再起这个。

## WebUI 配置顺序

### 1. 115 官方接口（扫码登录）

设置页 →「115 官方接口」→ 扫码登录 → 用手机 115 App 扫 → 确认。

- access_token 2 小时过期，refresh_token 自动续期，**不会掉线**。
- `client_id` 复用 plex-demo 已备案的应用，你不需要去 115 开放平台申请。
- 退出登录也在这里；退出后播放会回退到网页 Cookie（如果填了）。

### 2. Plex

| 项 | 填什么 |
|---|---|
| Plex 地址 | `http://127.0.0.1:32400` |
| X-Plex-Token | Plex Web 任意影片页源码里 `X-Plex-Token=` 后面连续 19~20 位 |

Plex 设置 → 网络 →「自定义服务器访问 URL」填 `http://NAS的IP:32500`，客户端连 32500，302 才能生效。

### 2.5 115 Cookie 怎么来：扫码，不用再开 F12

设置 → **115（Cookie）** → 点「扫码获取 Cookie」，用 115 App 扫一下并确认，Cookie 会自动写入并保存。

- 和 CMS 的「115扫码登录」是同一条路：网页扫码 → 换取 `UID/CID/SEID/KID`
- 和上面的「115 官方接口」扫码是两回事：那个换的是开放平台 token，只给播放用
- 手动粘贴 Cookie 的老办法仍然有效，两者等价

### 3. 路径映射（关键）

把「Plex 里看到的路径」翻译成「115 网盘里的路径」。

| 列 | 含义 | 你的例子 |
|---|---|---|
| Plex 前缀 | Plex 容器/挂载里的路径 | `/media` |
| 云盘前缀 | 115 网页版里的路径 | `/media` |
| CD2 前缀 | 仅「扫描前刷 CD2 目录缓存」用，可留空 | 留空 |

例：Plex 里是 `/media/电影/沙丘2.mkv`，115 网盘里也是 `/media/电影/沙丘2.mkv` → 两列都填 `/media`。

> 第一列不能留空（留空这条映射会被丢弃）；第二列留空会当成 `/`，等于从网盘根目录开始找。

### 4. 自动入库（115 事件）

| 项 | 默认 | 说明 |
|---|---|---|
| 启用 | 开 | 关掉就只剩定时扫描，会漏移动 |
| 拉取间隔 | 60 秒 | 事件流水轮询间隔，实际会加 0~15% 抖动 |
| 目录静置 | 90 秒 | CMS 还在动就继续等 |
| 最长等待 | 600 秒 | 目录一直有事件也不无限等 |
| 扫完复核 | 180 秒 | 接住「扫的时候还没写完」 |
| 目录冷却 | 120 秒 | 同一目录两次扫描的最小间隔，防事件风暴 |
| 最近文件兜底 | 关闭 | 可选保险，默认关（115 对 `/files*` 拦截最严） |
| 每日全量 | 关闭 | 需要时在设置里开，默认关（最重的一步） |

**115 Cookie 只用于这里**（事件接口是网页版的，官方开放平台没有「最近操作」）。填一次即可，失效时 WebUI 会提示。

> 这里触发的「扫描」是 **Plex 的局部刷新接口**（`GET /library/sections/{id}/refresh?path=...`），不碰 115 网页接口；移动事件的处理全程只查本地索引，一次 115 请求都不发。对 115 的固定开销只有事件流水轮询（60 秒一次，带抖动）。

### 5. CloudDrive2（可选）

填了 CD2 gRPC 地址（默认 `127.0.0.1:19798`）后，扫描前会先让 CD2 刷新目录缓存，避免刚整理完 Plex 扫到空目录。

## 直链来源：固定 115 官方接口

和 plex-demo 完全同一条链路，没有第二个选项：

```
Plex 请求 /library/parts
  → POST proapi.115.com/open/folder/get_info  {path}      1 次，按完整路径定位 pickcode
  → POST proapi.115.com/open/ufile/downurl    {pick_code} 1 次，换直链
  → 302
```

之前提供过「纯 Cookie / AList / CD2 / 自定义接口」几个选项，已经删掉了：

- **纯 Cookie** 要逐级列目录（一个文件 3~4 个请求），首次起播慢，还更容易撞风控
- 其余几个都需要额外维护一套凭据，对这个场景没有收益

官方接口临时不可用时（token 过期、proapi 抽风），代码会**自动回退**网页 Cookie 兜底一次；再失败就回源 Plex，播放不会中断。

> 老配置里的 `provider.type` 会在保存时被强制改成 `open115`，不需要你手动改。

## 企业微信（只发通知，字段与 CMS 对应）

本工具的定位很明确：**只往企业微信发通知，不接收消息**。

- 不占用企业微信的「API 接收消息」地址，所以 CMS 的微信菜单照常可用，两者可以同时用同一个自建应用
- 推送是各发各的，同一时间发也不冲突

在「设置 → 通知（企业微信）」里，照 CMS 那一页抄这 4 项就够：

| 本项 | CMS 里的名字 | 作用 |
|---|---|---|
| 企业ID | 企业ID | `ww...`，获取 access_token 用 |
| 应用Secret | 应用Secret | 同上，只保存不显示 |
| 应用ID | 应用ID | AgentID，发消息用 |
| 接收人 | —（CMS 没有） | `@all` 或 UserID，多个用竖线分隔 |
| API代理 | API代理 | 选填。`http://ip:port` 走正向代理；反代域名则替换接口基址，两种自动识别 |

CMS 那页里的 **Token / EncodingAESKey** 是「接收消息」用的，本项目用不到，不用填、也没有对应输入框。

常见报错：

| errcode | 含义 | 处理 |
|---|---|---|
| 60020 | 出口 IP 不在「企业可信IP」 | 把 NAS 出口 IP（或 API 代理那台服务器的出口 IP）加进应用的可信 IP |
| 40013 | 企业ID 不对 | 检查 `ww` 开头那串 |
| 40056 / 60011 | 应用ID 不对或应用不在可见范围 | 检查 AgentID、应用可见范围 |
| 81013 | 接收人不存在 | 检查 UserID，或先用 `@all` |

> 配置完点「发送测试消息」，失败时会直接把企业微信返回的 errcode 显示出来，不用去翻日志。

## 常见问题

**Q：为什么还要填 115 Cookie？不是全官方了吗？**
A：播放确实全官方。但 115 开放平台**没有**「最近操作」接口，移动/改名事件只有网页版能看到——那正是 plex-demo 漏入库的原因。Cookie 只用来拉事件，不参与播放。

**Q：不填 Cookie 行不行？**
A：行，播放正常，但只剩定时扫描 + 每日全量，移动进 media 的文件要等下一次全量才能被 Plex 看到。

**Q：扫码一直不成功？**
A：二维码 5 分钟过期，重新点一次。如果状态一直「超时」，多半是 NAS 到 `qrcodeapi.115.com` 线路问题，换个 DNS 或稍后再试。

**Q：302 不生效，日志里 `[直链]` 一直失败？**
A：先看「测试直链」报什么。`115 里找不到路径：/xxx` = 云盘前缀填错；`401/未登录` = 去扫码；`回源` = 直链被限速，检查 UA 是否被改写（播放器 UA 必须原样透传）。

**Q：WebUI 打不开 / 登录之后一直转圈，日志也停在某一条不动？**
A：这是 v1.8.12 及以前的阻塞 bug，v1.8.13 已修。当时解析播放和发企业微信通知都在 uvicorn 的事件循环里同步等 HTTP：Plex 慢 10 秒、企业微信代理卡 40 秒，这期间 `/login`、`/health`、日志接口全部排队，表现就是「工具进不去」，而日志因为写不进去看着像空白。

- 立刻恢复：`docker compose restart plex302`（或 `docker restart plex302`）
- 根治：拉 v1.8.13，播放路径查询丢进线程 + 6 秒硬超时，通知改成后台线程发送，慢后端只影响自己
- 判断是不是这一类问题：`docker exec plex302 curl -s -o /dev/null -w '%{http_code} %{time_total}\n' http://127.0.0.1:999/health`，如果这个都超过 2 秒，就是事件循环被堵了

**Q：播放一直失败，怎么一次定位？**
A：在 NAS 上跑一条命令，它会从 Plex 里随便取一个真实视频，把整条链路走一遍：

```bash
docker exec -it plex302 python -m app.selftest
```

输出形如：

```
1. ✓ Plex Token 已配置
2. ✓ 115 官方接口已登录        selftop（剩余 7200 秒）
3. ✓ 路径映射已配置            ①/mnt/cd2/115/media → ②/media
4. ✓ 从 Plex 取一个真实视频    电影/沙丘2 → /mnt/cd2/115/media/电影/沙丘2.mkv
5. ✓ 路径映射命中              → /media/电影/沙丘2.mkv
6. ✓ 115 按路径定位到文件       pick_code=xxxx
7. ✓ 115 返回直链              来源=115open
8. ✓ 直链真的能下载            HTTP 206 · video/x-matroska · 收到 1024 字节
```

**哪一步红，就是哪一步的问题**，并且会直接给出改法。可以只测某个文件：

```bash
docker exec -it plex302 python -m app.selftest --path "/mnt/cd2/115/media/电影/xxx.mkv"
```

自检全绿但播放器还是不行，那问题在客户端或 Plex 远程访问，不在 302：

```bash
docker logs plex302 2>&1 | grep Plex302 | tail -5
```

- 有 `action=redirect` → 302 生效了，看直链是否被客户端拒绝（UA 绑定）
- 有 `action=proxy reason=...` → 看 reason，多半是映射/排版
- **一行都没有** → 播放请求根本没到 plex302，检查 Plex「自定义服务器访问 URL」是否指向 32500 入口

**Q：映射路径填错了会怎样？怎么检查？**
A：会「静默回源 Plex」——播放走 NAS 上传，不报错，看着就像 302 坏了。v1.8.13 起：

1. 设置 → 路径映射 → 点 **「对照 Plex 实际路径」**，程序直接读 Plex 自己上报的媒体库路径，逐条告诉你命中没命中，没命中的可以一键拿来当①
2. 播放时若映射没命中，日志会写一条 `[302] 路径映射未命中，回源 Plex：<路径>（当前①前缀：...）`
3. 「测试直链」现在会把 `Plex 路径 → 命中前缀 → 云盘路径` 三步都摊开

最常见的错是**①填得太短**：Plex 里是 `/mnt/cd2/115/media/...`，①只填了 `/mnt/cd2`，于是云盘路径变成 `/115/media/...` —— 多出来的 `115` 是 CD2 的挂载点名，网盘里根本没有这层。正确写法是 ①`/mnt/cd2/115/media`、②`/media`。

**Q：外网播放不了，日志里也什么都没有？**
A：先看日志页顶部「302 直链」是不是正常。播放请求必须走 **32500** 这个入口（nginx），只有它才会拦 `/library/parts` 并写 `[302]` / `[回源]`。常见三种：

1. Plex 的「自定义服务器访问 URL」填错（填成 WebUI 的 999 端口）→ 请求压根没到 32500
2. 反代只映射了 WebUI，32500 没映射，或被套了 Basic 认证（Plex 客户端不会发凭据）
3. 115 解析太慢：`/api/resolve` 超过 8 秒就放弃 302、回源 Plex，日志会留下一条 `[回源] ... resolver-timeout`

> v1.8.9 起解析有硬超时，后端卡住也不会让播放无限等待，一定会回源并在日志里留痕。
> v1.8.10 起风控冷却期不再「睡等」：剩余冷却超过 3 秒直接跳过本次请求、快速回源，播放不会被一个 405 卡住两分钟。

**为什么比 plex-demo 慢？** plex-demo 只会走官方接口（路径 → pickcode 一次定位，2 个请求）。如果你的「直链来源」还是老版本默认的 **115 纯 Cookie**，首次播放要逐级列目录（一个文件 3~4 个请求，遇到风控冷却更慢）。确认方式：设置 → 直链方式，选 **115 官方接口**；启动日志里也会直接提示。

**Q：会不会半夜把 115 扫爆？**
A：不会。事件驱动只扫变化的目录；全量扫描默认在 04:30 且可关。官方接口按路径定位，一次请求一个文件，不遍历。

## 日志页怎么看

日志不再是几千行文本，每条都带**级别**和**业务模块**，页面顶部还有两条辅助信息：

**① 可用性条**（本地判断，不发外部请求）

| 组件 | 什么时候显示「不可用」 |
|---|---|
| Plex | 没填 X-Plex-Token |
| 局部入库（Cookie） | 没填 Cookie（事件流水与入库全停） |
| 官方接口（播放） | 没扫码登录，播放会回退 Cookie 逐级解析 |
| 302 直链 | 直链来源设为 none（全部回源 Plex） |
| CD2 | 没填 gRPC 地址（不影响播放，只是扫描前不预刷目录缓存） |

**② 问题摘要**：只列出现错误/警告的模块，点一下就筛到该模块。比如「扫描入库 2 错误 · [扫描] Plex 局部刷新失败：timeout」，一眼知道是 Plex 不支持还是 115 被拦。

**③ 日志正文**：`时间 | 级别 | 模块 | 消息` 四列对齐。级别分为 `INFO / WARN / ERROR`，可切「全部 / 重要（WARN+ERROR）/ 错误（仅 ERROR）」；模块可下拉筛选；搜索框支持任意关键字（如 `405`、`风控`、片名）。

模块划分：`事件入库`、`115接口`、`扫描入库`、`播放302`、`Plex`、`CD2`、`配置`、`通知`、`WebUI`、`系统`——直接对应代码里的日志前缀，不额外改输出格式。

「清空」只清 WebUI 的内存缓冲，`/config/logs/app.log` 保留，方便事后翻。

```
  nginx/         njs 拦截、共享内存直链缓存、回源兜底
```
